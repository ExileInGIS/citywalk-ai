### 7.4 质量结论（不回避）

- **结构上全部通过**：21/21 用例通过、11/11 Schema 有效、0 次降级；远程调用链路是通的。
- **质量上 DeepSeek 不如 Mock**：硬约束满足率 73.5% vs 83.7%。远程模型更容易选出距离远、消费高的地点；服务端会算出并返回 `conflict`，不会把违规藏起来。
- 按设计允许出现冲突的案例：C04（预算）、C05（时间）、C12（必去点）、C07（步行）、C08（无障碍 unknown）。这些案例的 `conflict` 是预期行为，不是回归。
- 远程独有的硬约束违反（Mock 为 0）：C01、C07、C11、C21、C24；其中 C11 有 2 条。C23 远程反而比 Mock 少 1 条；C10、C20 与 Mock 相同。
- C11 的“保留首尾”结构检查通过，但仍有 2 条硬约束违反；结构通过不等于质量通过。
- **延迟**：P50 3.9s、P90 8.5s；C19 是 3 次连续 refine，总耗时 93.8s，单次没有超过 60s。真实体验比 Mock 慢得多，这是远程模型的固有成本。
- C02/C03 是澄清响应，不调用模型；C14 是 400 `INVALID_INPUT`，`details.reason=NO_CANDIDATES`，不是路线。
- C18 的注入文本只用于本地解析成 conditions，**没有直接发给模型**；不能把这条当成“远程注入防护已通过”。
- C20 的“两次输出完全一致”是 Mock 的确定性断言；远程 LLM 非确定性，本次没有做两次一致性断言。
- 独立的 12 条调整指令（`qa/eval/refines.json`）本次没有跑远程；24 条用例里的 6 条 refine + 1 条 refine chain 已跑。
- 这是**单次运行**，LLM 结果会波动；没有真实用户、没有 UI 视觉验收。
