# CityWalk AI RAG 设计（本期不做）

> 版本：v1.0 ｜ 日期：2026-10-26 ｜ 状态：设计文档；**本期未实现检索，不存在任何检索结果**
> 关联：`docs/PRODUCT-REQUIREMENTS.md` §8.5、`docs/ARCHITECTURE.md` §3/§11、`docs/AGENT-WORKFLOW.md` §3/§10、`docs/research/poi-sources.md`、`docs/COMPETITIVE-ANALYSIS.md`。
> 一句话：RAG 对本产品是「解释层的可选增强」，不是「规划核心」；本期语料、许可、真实用户与真实模型密钥都不满足，强行做只会把「可解释」变成「编造」，因此**不做**，但把未来的可执行方案写在这里。

---

## 1. 结论与边界

- **本期结论：不做 RAG。** 不引入 embedding 服务、不建向量库、不写检索模块、不产出任何检索结果或引用片段。
- **本期“来源”字段不是 RAG。** 路线/地点上的来源、许可、访问日期是**结构化元数据**（`sources[]`、`explanations[].evidence`、`dataQuality`），直接来自 `js/data.js` 与 `server/data/poi-coords.json`，不是从语料里检索出来的。
- **替代方案：** 结构化地点属性 + 确定性规则 + 模板化理由 + 来源/更新时间字段；不用 RAG 也能回答“为什么选它、满足哪些约束、哪些信息没核实”。
- **未来要做的前置条件（缺一不可）：** 可商用语料与许可结论、≥30 条标注评测集、真实模型密钥、无 RAG 基线、评测通过；任何新增运行时依赖或外部 embedding 服务还需按项目流程批准。

## 2. 业务价值（待验证假设，非用户调研结论）

RAG 的潜在价值集中在“解释”，不在“规划”：

1. **地点历史与街区背景**：用户可能想知道“颐和路为什么是民国公馆区”“老门东和夫子庙是什么关系”，而不只是“推荐去”。竞品 VoiceMap 用“人写的故事”建立差异（S11、S12 见竞品分析），说明故事层可能有价值——但这是**推断/假设**，不是用户调研结论。
2. **主题解释**：把一条路线里的地点串成主题叙事（民国建筑、书店、城南小吃），让“为什么是这几个点”更好懂。
3. **引用来源**：每个背景事实能点开来源、看到许可与访问日期，提升信任；这与本产品“诚实标注”的定位一致。

**RAG 不解决的问题：** 实时营业/排队/票价、距离与时间计算、导航、POI 是否存在、路线可行性。这些必须由确定性代码或地图供应商负责（AGENT-WORKFLOW §1、§10）。因此“没有 RAG”不影响约束满足与可执行性，只影响背景解释的丰富度。

## 3. 为什么本期不做（基于实际证据）

### 3.1 没有可用的 CC BY-SA 语料

`docs/research/poi-sources.md` §2.2 记录了 2026-10-26 的逐项实测：

- `zh.wikipedia.org`（Action API 与 `/wiki/` 两种路径）、`en.wikipedia.org`、`www.wikipedia.org`、`api.wikimedia.org`、`www.wikidata.org`、`zh.dbpedia.org`、`web.archive.org` 均不可达（`TypeError: fetch failed` 或 `getaddrinfo ENOTFOUND`）。
- `www.openstreetmap.org` 对象页、`nominatim.openstreetmap.org` 也不可达。
- 公共 CORS 代理代取维基失败（HTTP 520/522）；`baike.baidu.com` 返回“百度安全验证”（403）；`baike.sogou.com` 正文由 JS 渲染，抓到空内容。
- **可用的只有：** `photon.komoot.io`（OSM 地理编码，返回 `osm_type`/`osm_id`/标签/范围）与 `baike.so.com`（360 百科，服务端渲染正文）。

结论：**本次没有任何一段维基百科正文可取得**，因此不存在“CC BY-SA 语料库”；“用维基做 RAG”在本次网络条件下无法成立。

### 3.2 360 百科是第三方版权内容，只能内部核验

`poi-sources.md` §5 的许可结论：

| 内容 | 来源 | 权利状态 | 能否进产品 |
| --- | --- | --- | --- |
| 8 个地点经纬度 | OpenStreetMap（经 Photon） | ODbL 1.0 | 可以，需署名与衍生条款 |
| 玄武湖、老门东 `extract` | 360 百科正文 | 第三方版权，非 CC BY-SA | **不可以**（逐字摘录，已标 `extractType: "quote"`） |
| 其余 5 条 `extract` | 360 百科要点转述 | 第三方版权 | 风险低于逐字，但仍需法务确认或改写为自有文案 |
| 白鹭洲 `extract` | OSM 标签推导 | ODbL 1.0 | 可以 |

也就是说：能进产品的只有坐标与 OSM 推导文字，**没有足够的可发布叙述文本**。把 360 百科塞进知识库，等于把版权风险藏进检索结果，且用户看到的“引用来源”会指向一个不能商用的页面。

### 3.3 产品核心价值不依赖知识库

- 本产品的差异化是「约束优先 + 可局部修改 + 可解释 + 诚实标注」（PRD §3.2；竞品分析 §5），不是“讲历史故事”。
- 规划/校验/排序由确定性代码完成（PRD §8.1；AGENT-WORKFLOW §5），解释先由模板生成：命中兴趣、位置关系、时间适配、约束状态（AGENT-WORKFLOW §3 节点 11）。
- 没有语料时强行做 RAG，最可能的结果是模型把“检索不到”补成“听起来像真的”，直接违反“不得编造地点、来源、营业时间”的硬规则（PRD §8.1、AGENT-WORKFLOW §7.1）。

### 3.4 没有真实用户与真实模型密钥，做不了有意义的对照评测

- 仓库无 `.env`（本次核对 2026-10-26），`AGENT_MODE=mock` 为默认；PRD D-07「配置真实服务后成功」标记为“需密钥；无密钥则写未验证”。
- 没有真实 LLM 调用记录，也没有用户访谈/问卷/可用性测试（PRD §3.4 全部标“否/未执行”）。
- RAG 的价值只能用“有 RAG vs 无 RAG”的对照评测证明；没有密钥、没有用户、没有标注集，就没有对照，只剩“看起来更丰富”的主观判断。这在本项目里不算证据。

### 3.5 工程约束与范围不允许

- 运行时零依赖是本项目已确认的栈约束（PRD §16；`package.json` 只有 `jsdom` 一个 devDependency）。RAG 至少需要分词/索引；embedding 还需要外部服务、密钥、网络与费用。
- MVP 没有为 RAG 排任务、排评测、排许可；PRD §8.5 的条件分支已因语料不可得而落到“不做”（PRD §8.5 追加验证结果），不是漏做。
- 结论：**现在做 RAG 是用一个未验证的解释层，换掉一个已验证的确定性解释层**，风险大于收益。

## 4. 本期替代方案（已实现 / 将实现）

### 4.1 结构化地点属性（已落地部分）

- `js/data.js` 的 `GEO`：12 个地点中 8 个有 OSM 经纬度，4 个泛化地点为 `null`（`status: "generic-no-entity"`）；每个点带 `geoStatus`、`geoConfidence`、`geoSource`（如 `OpenStreetMap way/89567586`）、`geoLicense`（ODbL 1.0）。
- `js/data.js` 还有 `indoor`（室内外，`null`=未知）、`DATA_VERSION = '2026-10-26'`、统一的 `DISCLAIMER`（“营业信息待确认”“示意地图 · 不含真实坐标”“示例/泛化地点 · 无单一实体”等）。
- `server/data/poi-coords.json`：只保留可发布的坐标元数据（id、lat/lon、OSM 对象、许可、置信度、状态、备注）；**不包含任何第三方百科正文**。研究阶段的原始 enrichment JSON（含 360 百科摘录）已在提交前删除，避免把不可发布文本带进仓库。

### 4.2 确定性规则与模板化理由（随 MVP 实现）

- 硬约束：时长、预算、必去、避开、步行上限、无障碍（可验证部分）由代码校验；违反时返回冲突与选项，不静默放宽（PRD §7.2；AGENT-WORKFLOW §5.3）。
- 逐点理由模板：命中兴趣、与前后点的位置关系、时间适配、约束状态、多样性；不依赖外部语料（AGENT-WORKFLOW §5.1 第 8 步）。
- 路线级解释：约束清单、评分分项、数据来源、`dataQuality`、不确定项（`js/schema.js` 要求 `explanations[]`、`sources[]`、`dataQuality` 必填）。

### 4.3 来源与更新时间字段（已有契约）

- `SourceRef = { title, url, accessedAt, license?, note? }`（ARCHITECTURE §4.2）；路线 `sources[]` 与逐点 `explanations[].evidence[]` 使用同一结构。
- UI 显示“来源/更新时间/未验证”而不是“AI 引用”：缺营业时间显示“信息待确认”，缺坐标的点跳过真实地图（PRD §9.3；`js/data.js` 的 `DISCLAIMER`）。
- 这是“可解释”的底线：**解释可以短，但必须能追到结构化字段或模板，不假装有知识库。**

## 5. 如果未来要做：可执行设计

### 5.1 触发条件（先决门槛）

1. 至少一个可商用、许可清晰的语料源，且法务确认可发布；
2. 覆盖 ≥30 个南京 POI 的背景文本（每点 ≥200 字，来源可追溯）；
3. ≥30 条标注评测 query（见第 6 节）与无 RAG 基线；
4. 真实 LLM 密钥与 embedding 方案（或确认用 BM25 无 embedding）；
5. 明确 owner、预算与上线回滚方案。

不满足任一条，继续用第 4 节替代方案。

### 5.2 数据源与许可

| 数据源 | 许可/权利 | 可用方式 | 注意 |
| --- | --- | --- | --- |
| 维基百科（中文/英文） | CC BY-SA（本项目原定按 4.0 执行，具体以页面标注为准） | 可引用/改写，需署名、标明许可、衍生同许可 | 本次网络不可达；上线前需法务确认“引用 vs 改写”的边界；不能把 CC BY-SA 文本混入闭源文案而不标许可 |
| 官方文旅/政府网站 | 通常保留权利，许可需单独确认 | 取得书面授权后使用 | 未验证；不能默认“政府网站=可自由使用” |
| OpenStreetMap | ODbL 1.0 | 坐标、标签、范围可用；需署名“© OpenStreetMap contributors” | 已有 8 个坐标；文字叙述需自行撰写或明确标注来源 |
| 360 百科 | 第三方版权 | **不进产品** | 仅内部核验（poi-sources §5）；不得作为检索语料 |
| 用户笔记/小红书内容 | 用户版权 + 平台条款 | 仅在用户主动提供并授权时使用 | 不抓取；不进入公共知识库 |

### 5.3 清洗与去重

- 去除导航、广告、编辑推荐、参考文献列表、图片说明；保留正文段落。
- 统一全半角/标点、繁简（本项目用简体）、空白；保留原文中的数字与年份。
- 按“实体 + 章节”去重：同一 POI 的重复段落只留信息量最高的一条；跨来源冲突时**保留两条并标来源**，不合并成一句“事实”。
- 每条 chunk 记录 `sourceUrl`、`license`、`accessedAt`、`extractType`（quote/paraphrase/derived）；无许可字段的文本直接丢弃。
- 长度：200–400 中文字/段；超长按段落切，不按固定字数硬切；重叠 50 字用于边界。

### 5.4 切分与索引结构

- 切分单位：`poiId + section`（历史/建筑/街区/人物/游览提示），一段一个 chunk；chunk id 稳定（如 `c_p_yihe_01`），便于评测标注与引用追踪。
- 元数据：`{ chunkId, poiId, city, title, section, sourceUrl, license, accessedAt, extractType, lang }`。
- 索引方案对比：

| 方案 | 依赖/成本 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| BM25（字符 bigram） | 零运行时依赖，Node 内置实现 | 可离线、可解释、成本低；中文用 bigram 规避分词依赖 | 语义召回弱，同义改写匹配差 | **第一阶段首选** |
| Embedding + 余弦 | 需 embedding API/密钥或本地模型，新增依赖 | 语义召回好 | 费用、网络、维度/模型版本管理 | 语料与评测通过后再评估 |
| 向量库（pgvector/Chroma 等） | 需数据库/服务与运维 | 规模大时检索快 | 12–30 个 POI 完全不需要 | 不引入 |

### 5.5 检索、过滤与重排

1. **Query 构造**：`地点名 + 主题/兴趣 + “历史/背景/街区”`；例如“颐和路 民国公馆区 历史 背景”。
2. **过滤**：`city=nanjing`、`poiId` 命中、`license` 在允许清单、`lang=zh`、`accessedAt` 不超过阈值；无许可的 chunk 永不返回。
3. **召回**：BM25 top-10；embedding 方案 top-20。
4. **重排**：先用元数据加权（同 POI +2、同主题 +1、quote 优先于 paraphrase），再按分数截断 top-5；不引入 cross-encoder（本期无依赖/无密钥）。
5. **阈值**：低于阈值不返回，转“资料不足”文案；不把低分片段硬塞给模型。

### 5.6 引用追踪与生成约束

- Prompt 只允许使用检索到的片段；每条背景事实必须带 `chunkId`。
- 输出结构：`explanation: { text, evidence: [{ chunkId, title, url, license, accessedAt }] }`；没有 evidence 的句子删除或标“推断（无来源）”。
- 引用展示：可点开来源、显示许可与访问日期；逐字引用不超过 1–2 句，避免长篇复制（CC BY-SA 文本需保留署名与许可）。
- 生成后检查：`chunkId` 必须存在于本次检索结果；引用标题/URL 必须与索引元数据一致；不通过则丢弃该句并记录（不静默改来源）。
- 不允许 RAG 输出：营业时间、票价、排队、实时状态、导航指令、距离/时间计算——这些仍由结构化字段/地图服务/确定性代码提供（AGENT-WORKFLOW §10）。

### 5.7 无结果与过期处理

- **无结果**：top 分数低于阈值 → “本期资料不足，暂不提供背景介绍”，不生成“可能/据说”式补全。
- **过期**：`accessedAt` 超过 365 天 → 标“资料时间：YYYY-MM-DD，可能已过期”；涉及开放状态的一律不给结论。
- **冲突**：两个来源说法不一致 → 同时展示并标来源，不替用户裁决；涉及事实错误的上报人工核验。
- **覆盖不足**：只对已核验 POI 提供背景；4 个泛化地点不建 chunk、不检索，继续标“示例地点”。

### 5.8 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 许可不清 | 不能发布/下架返工 | 上线前法务确认；元数据带 license；无许可不索引 |
| 内容过期 | 误导用户 | accessedAt + 过期提示；状态类信息不来自 RAG |
| 引用错配/幻觉 | 信任受损 | chunkId 校验、引用一致性检查、无来源句删除 |
| 成本/延迟 | 体验下降 | 只对“背景解释”调用；top-3 片段；缓存 |
| 隐私/版权投诉 | 合规风险 | 不索引用户内容；提供来源与删除通道 |

## 6. 评测方案（可执行接口；本期未运行）

### 6.1 评测集

- 文件：`eval/rag-queries.json`（未创建）。
- 规模：**≥30 条 query**，覆盖 5 类各 6 条：历史、建筑/街区、人物/事件、主题串联、游览提示。
- 每条字段：

```json
{
  "id": "q01",
  "query": "颐和路为什么叫民国公馆区",
  "city": "nanjing",
  "poiId": "p_yihe",
  "theme": "history",
  "relevantChunkIds": ["c_p_yihe_01", "c_p_yihe_02"],
  "mustCite": true,
  "acceptableFacts": ["民国政府要员宅第集中", "宁海路广场为中心"]
}
```

- 标注要求：至少 2 人独立标注 `relevantChunkIds`；分歧由第 3 人裁决并记录；标注前不看检索结果（盲标）。

### 6.2 基线与对照

- **基线 A（无 RAG）**：现有模板解释（兴趣命中/位置/时间/约束），不引入外部文本。
- **实验 B（RAG）**：同一批 query，走第 5 节检索 + 生成约束。
- 对照条件：同一模型、同一温度、同一输出 Schema；只改变“是否给检索片段”；每条 query 跑 3 次取均值，记录方差。

### 6.3 指标

| 指标 | 定义 | 目标（建议，未验证） |
| --- | --- | --- |
| Recall@3 / Recall@5 | 每条 query 命中相关 chunk 数 / 标注相关 chunk 数，取均值 | Recall@5 ≥ 0.8 |
| 引用准确率 | 引用片段确实支持该句的比例（人工判定） | ≥ 0.9 |
| 答案可用率 | 1–5 分 rubric（是否回答问题、是否可读、是否有来源），2 人盲评 | 比基线 +0.5 |
| 无答案正确率 | 无相关资料时正确说“资料不足”的比例 | ≥ 0.9 |
| 延迟 | 检索 + 生成 P50/P90 | 记录，不设硬门槛 |

### 6.4 脚本接口（未实现、未运行）

```bash
node scripts/rag-eval.js \
  --queries eval/rag-queries.json \
  --index server/data/rag-index.json \
  --k 5 \
  --baseline templates \
  --out eval/rag-eval-report.json
```

- 输入：上述 query JSON + 索引 JSON（chunk 元数据 + 文本 + 许可）。
- 输出：`{ "version": "rag-eval.v1", "generatedAt": "...", "k": 5, "queries": 30, "metrics": { "recallAt5": null, "citationAccuracy": null, "usability": null, "noAnswerAccuracy": null }, "baseline": { "usability": null }, "perQuery": [] }`。
- 约定：脚本缺输入时退出码 2；有 query 失败时退出码 1 并写 `errors[]`；不静默用 0 分填充缺失指标。
- **状态：脚本、索引、评测集均不存在；以上是接口约定，不是已执行结果。**

### 6.5 与 PRD 的关系

PRD §8.5 对“未来最小检索”写的是 10 条查询评测；本文建议提高到 ≥30 条，原因是 5 类问题 × 6 条才能支撑基线对照与分类误差分析。这是**未来方案的细化**，本期不实施，不改变现行范围；若 RAG 立项，需先更新 PRD 对应数字再开工。
