## 0. 一页摘要

**一句话**：用户用自然语言说清「什么时候、和谁、有多少时间、多少钱、想逛什么」，CityWalk AI 返回一条**满足硬约束、顺序可执行、理由可解释、可继续用自然语言修改**的城市漫步路线。

**本次升级要解决的真问题**：现有仓库是一个可点击的高保真原型，但 AI 是本地模拟、没有服务端、没有结构化契约、没有可复现测试。用户能「看到」产品，却不能真正「用一个 AI 服务」完成规划。本次把原型升级为**可运行、可接入真实服务、可验证、可部署的 MVP**。

**本次不做**：真实实时 POI/营业状态、真实导航/路网、账号体系、支付、公网发布。原因与替代方案见第 15 节。

**成功标准（可检查）**：
1. 不配置任何密钥，`node server/index.js` 启动后，浏览器可完成「输入 → 澄清 → 生成 → 自然语言调整 → 保存/导出」完整闭环，且所有 Mock 结果都有明确标识；
2. 配置真实 LLM 后，同一前端通过 `POST /api/agent/run` 获得结构合法的路线；服务失败时按配置降级，界面显示 `degraded`；
3. `pnpm test` 在干净环境可复现通过；评测脚本对固定测试集输出真实指标，报告中每个数字都能重跑；
4. 代码、文档、界面三处的「已实现 / 模拟 / 未验证」口径一致。

## 1. 产品背景与目标

### 1.1 背景

城市漫步（CityWalk）用户的实际决策不是「找一个地点」，而是「在有限的时间、预算和体力内，把几个地点排成一条走得通、值得走的路线」。地图产品擅长单点检索与导航，旅行攻略擅长种草但不可执行，AI 行程产品擅长生成文本但常缺少硬约束校验与可解释性。

现有 CityWalk AI 原型已经验证了「AI 对话 + 需求配置 + 地图 + 路线卡片 + 动态调整」的产品形态，但：
- AI 全部为浏览器本地规则，无法接入真实模型；
- 没有服务端接口、没有请求追踪、没有结构化输出校验；
- 地图为 SVG 示意，没有真实坐标与 Provider 实现；
- 测试依赖作者本机环境，不可复现；
- 无障碍与响应式不达可交付标准。

### 1.2 产品目标（本次升级）

| 目标 | 说明 | 验证方式 |
| --- | --- | --- |
| G1 真实闭环 | 从自然语言到可执行路线、再到自然语言调整，全流程可操作 | 浏览器手测 + jsdom 集成测试 |
| G2 服务可接入 | 统一 `/api/agent/run`，Mock/Remote 可切换，失败可降级 | API 测试 + 故障注入测试 |
| G3 约束可信 | 硬约束由确定性代码校验，冲突必须解释并由用户决策 | 规则单测 + 冲突场景用例 |
| G4 结果可解释 | 每个地点有推荐理由，整条路线有评分口径、约束清单、数据来源与不确定项 | 评测 + UI 检查 |
| G5 工程可复现 | 一条命令启动、一条命令测试、评测结果可重跑 | 干净环境验收 |
| G6 诚实交付 | 模拟/真实/未验证三种状态在界面与文档中一致 | 文档-代码对照审查 |

### 1.3 非目标（本次明确不做）

- 不做实时营业状态、排队、票价、预约、导航转向；
- 不做账号、云端收藏、多端同步、支付；
- 不做公网部署与正式上线（无凭据/网络条件，见第 15 节）；
- 不做多城市真实 POI 数据（架构支持扩展，本次只交付南京示例数据）；
- 不做流式 LLM 输出（先稳定非流式；SSE 方案写入扩展设计，不声称已实现）。

## 2. 目标用户与使用场景

> 以下用户画像与场景是**产品假设**，来自需求方输入与竞品功能观察，**尚未经过真实用户访谈或问卷验证**。验证方法见第 3.4 节。

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 | 主要阻力 |
| --- | --- | --- | --- |
| A. 周末本地探索者（主） | 22–35 岁，城市白领/学生，熟悉城市但想换一种逛法 | 2–4 小时、预算有限、想按兴趣组合地点、少走回头路 | 攻略碎片化、路线要自己拼、走错顺序浪费时间 |
| B. 来城半日游客 | 25–40 岁，出差/短途旅行，时间紧 | 半天内看最有代表性的地点 + 本地体验，最好有明确结束时间 | 不知道地点之间距离与顺序、怕来不及 |
| C. 主题深度爱好者 | 摄影/建筑/书店/咖啡爱好者 | 按主题深度走，接受更多步行，想看完理由与背景 | 通用推荐太泛、缺少主题一致性与可解释性 |
| D. 同行组织者 | 带父母/孩子/朋友出行的人 | 控制步行强度、预算、无障碍与餐饮偏好，需要能解释给同行人 | 众口难调、改了需求要重新规划 |

### 2.2 典型场景

1. **临时起意**：周六 14:00，两个朋友在南京新街口，想逛 4 小时，喜欢咖啡、历史和拍照，预算 150 元，不想走回头路。
2. **信息不全**：用户只说「帮我规划一条 CityWalk」，系统追问城市与时长，而不是凭空假设。
3. **冲突决策**：用户坚持 3 个必去点 + 2 小时，系统算出至少 3 小时 20 分，给出「延长到 3.5 小时 / 去掉一个必去点 / 缩短每站停留」三个选项，由用户选。
4. **途中调整**：下雨了，用户说「下雨了，尽量安排室内活动」，系统替换露天点位，保留未受影响的部分，并说明哪些约束仍满足、哪些无法保证。
5. **改一个点**：用户说「把咖啡馆换成书店」，系统只替换该站，重算相邻步行与总时长，给出前后差异。
6. **保存与分享**：用户把路线保存到本地，导出 Markdown 发给朋友。

### 2.3 用户旅程（目标态）

```
产生出行想法
  → 打开首页，用一句话描述 / 逐项补充（渐进式披露）
  → AI 解析并回显「我理解到的条件」，缺失必填项时定向追问（最多 3 个问题）
  → 生成中：展示可感知的阶段（理解 → 检索 → 排序 → 校验），可取消
  → 结果：地图 + 时间线 + 摘要 + 约束清单 + 理由 + 数据可信度
  → 调整：自然语言指令 / 冲突选项 / 手动排序（重算并标注）
  → 保存到本地 / 导出 Markdown / 复制分享文本
  → 再次打开：从收藏恢复路线与条件
```

## 3. 用户问题与产品机会

### 3.1 核心问题（假设）

| # | 问题 | 现状证据 | 验证状态 |
| --- | --- | --- | --- |
| P1 | 地点推荐与「排成一条路」是两件事，用户要自己拼顺序 | 现有原型与竞品均以单点/列表为主（见竞品文档） | 待验证 |
| P2 | 时间、预算、体力、同行人、天气会改变「最优路线」 | 产品逻辑推演；无用户数据 | 待验证 |
| P3 | 改一处就要重填表单，用户更愿意说一句话 | 现有原型对话调整可用，但只覆盖 6 类 | 待验证 |
| P4 | 用户不知道 AI 为什么这样排，也不知道哪些信息没核实 | 现有原型有理由与免责声明，但无逐点证据 | 待验证 |

### 3.2 产品机会

**差异化定位**：不是「又一个 AI 行程生成器」，而是**约束优先、可解释、可局部修改的城市漫步规划器**。

- 约束优先：硬约束（时间/预算/必去/避开/体力）由确定性规则校验，不交给模型自由发挥；
- 可解释：每个点位给理由，整条路线给评分口径与约束清单；
- 可局部修改：自然语言只改受影响的部分，保留其余顺序与时间；
- 诚实：Mock、估算、未核实数据在界面上一眼可见。

### 3.3 竞品参照

竞品事实、来源与可信度见 `docs/COMPETITIVE-ANALYSIS.md`。本 PRD 只使用其中「可验证事实」列，推断与建议单独标注。

### 3.4 待验证假设与验证方法

| 假设 | 验证方法 | 成本 | 本次是否执行 |
| --- | --- | --- | --- |
| 用户愿意用自然语言修改路线 | 5 人可用性测试（任务：改一处并说明结果） | 中 | 否（无被试），列为上线前必做 |
| 约束清单能提升信任 | A/B 两版结果页对比理解度 | 中 | 否 |
| 2–4 小时是主流时长 | 埋点统计真实使用 | 低（需上线） | 否（无真实流量） |
| 用户接受「估算距离」 | 访谈 + 结果页可用性测试 | 低 | 否 |

> 本作品集**不声称**完成过用户调研；所有涉及用户偏好与转化的结论均标注为假设。

## 4. 功能需求及优先级

优先级：`must-have`（M）> `high-want`（H）> `nice-to-have`（N）。括号内为同类内排名；**任何 must-have 未完成不交付**。

### 4.1 需求输入与解析

| ID | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| F-01 | 自然语言输入（≤200 字），实时字数 | M(1) | 输入、清空、示例填充可用；超长截断有提示 |
| F-02 | 结构化条件：城市、起点/区域、时长、开始/结束时间、兴趣、预算、同行人、步行强度、交通方式、节奏、餐饮偏好、无障碍、天气、避开项、必去点 | M(2) | 分层展示：核心条件默认可见，高级偏好可展开；所有字段参与规划或有明确「未指定」 |
| F-03 | 自然语言与表单双向合并，回显「已识别条件」 | M(3) | 识别项同步到表单；冲突时以用户最后一次输入为准并提示 |
| F-04 | 必填检查与定向追问（最多 3 问，可跳过非关键项） | M(4) | 缺城市/时长不生成；追问有快捷选项；回答后继续原流程 |
| F-05 | 输入清洗与提示注入防护 | M(5) | 长度/字符限制；注入文本不改变系统行为；记录安全事件（不含原文） |

### 4.2 路线生成与校验

| ID | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| F-06 | 候选地点检索与过滤（城市、避开、必去、无障碍未知处理） | M(1) | 必去点必在路线中或显式冲突；避开项不出现 |
| F-07 | 路线排序与时间/预算/距离计算 | M(2) | 每站停留、站间步行、总时长、预算区间、距离可复算 |
| F-08 | 硬约束校验（时长上限、预算上限、必去、避开、步行上限） | M(3) | 每条硬约束有 `met/partial/violated/unknown` 状态；违反时给选项，不静默放宽 |
| F-09 | 可解释评分（兴趣/时间/效率/预算/多样性） | M(4) | 权重可配置；页面展示「为什么」；文档说明权重是初始假设 |
| F-10 | 冲突解释与三个可执行选项 | M(5) | 选项执行后重新校验并展示结果 |
| F-11 | 路线结构 Schema 校验（服务端 + 前端） | M(6) | 字段类型/范围/引用完整性；非法输出不渲染 |

### 4.3 结果展示与调整

| ID | 需求 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| F-12 | 结果页：地图 + 时间线 + 摘要 + 约束清单 + 理由 + 数据来源/更新时间 + 不确定提示 | M(1) | 三者联动；选中高亮；数据来源可点开 |
| F-13 | 自然语言调整 ≥8 类（少走路/换某类/更多某主题/预算/结束时间/保留首尾/下雨室内/不要类似） | M(2) | 每类有测试；局部保留；返回差异与未解决项 |

| F-15 | 手动排序 | H(1) | 支持上移/下移/拖拽；重算距离与时间，不再显示「未重算」 |
| F-16 | 冲突选项交互 | M(4) | 点选后执行并再次校验；不丢用户原始条件 |

## 5. 用户流程与异常流程

### 5.1 主流程（Plan）

```
填写/描述需求
 → 前端清洗（长度、空值、危险字符）
 → 本地解析 + 调 /api/agent/run(plan)
 → 服务端：意图=plan → 结构化条件 → 必填检查
     ├─ 缺失 → 返回 clarification（问题+快捷选项），前端展示，不生成
     └─ 完整 → 检索 → 过滤 → 排序 → 计算 → 校验
 → 冲突 → 返回 route + conflict(options)
 → 无冲突 → 返回 route
 → 前端渲染地图/时间线/摘要/约束清单
```

### 5.2 调整流程（Refine）

```
用户输入调整指令
 → 前端调 /api/agent/run(refine, {text, route})
 → 服务端：意图分类 → 解析目标（删/换/加/约束/保留）→ 局部修改
 → 重新计算受影响段 → 重新校验所有硬约束
 → 返回 {changed, reply, bullets, changes[], constraintsAfter, unresolved[], route}
 → 前端展示差异条 + 更新地图/时间线；冲突则展示选项
```

### 5.3 异常流程

| 场景 | 系统行为 | 用户看到 |
| --- | --- | --- |
| 缺城市/时长 | 不生成，返回澄清 | 「还需要两个信息」，快捷选项 |
| 必去点不存在 | 不静默删除，返回冲突与替代 | 「找不到这个地点」+ 建议 |
| 时间不足 | 返回冲突 + 3 个选项 | 冲突卡片，可点选 |
| 预算不足 | 优先换免费/低价点，仍超则冲突 | 预算说明 + 选项 |
| 步行超限 | 提示并给「减少一站/放慢节奏」 | 冲突卡片 |
| AI 超时 | 按 `fallback` 降级或报错 | 「已切换为本地模拟」+ 原因 |
| AI 返回非法 JSON | 最多 2 次修复；仍失败 → 标准化错误 | 「服务返回异常」+ 重试 |
| 地图加载失败 | 回退 SVG，保留列表/时间线可用 | 地图区域提示 + 重试 |
| 无候选地点 | 空状态 + 放宽建议（换城市/主题/时长） | 空状态卡片 |
| 用户输入注入 | 按数据处理，不改变系统行为 | 正常结果或通用错误；不泄露提示词 |

## 6. 核心页面说明

### 6.1 首页 · 规划工作台（保留现有左右布局）

- 左栏：标题、自然语言输入、快捷兴趣、渐进式高级筛选（新增：同行人、餐饮、无障碍、天气、避开、必去）、生成按钮、条件摘要、AI 助手。
- 右栏：未生成时精选路线 + 地点发现；生成中阶段进度；生成后结果区。
- 新增：**澄清卡片**（结构化问题 + 快捷选项）、**服务状态条**（Mock/Remote/降级/地图状态）、**调整前后差异面板**（可折叠，持久显示本轮改动）、**约束清单**、**数据来源与更新时间**、**导出/保存**。

### 6.2 路线结果区

路线摘要卡（名称、风格、总时长、地点数、距离、预算、评分简表）、地图（同步）、时间线（同步）、约束清单、理由、来源、免责声明、操作（收藏/重新规划/编辑条件/分享/导出）。

### 6.3 发现路线 / 我的收藏

保留现有页面；收藏改为 `localStorage` 持久化（可关闭），增加「导出」与「清除本地数据」；空状态与失效数据提示保留。

### 6.4 地点详情

保留；新增真实坐标/来源（若已核验）、室内外属性、无障碍信息状态、更新时间；未核验项明确显示「未验证」。

## 7. 业务规则与数据结构

### 7.1 条件模型（Conditions v1）

| 字段 | 类型 | 必填 | 默认 | 约束类型 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `city` | string | 是 | 无 | 硬 | 仅 `nanjing` 有完整数据 |
| `startLocation` | string | 否 | 空 | 软 | 文本，不参与精确路径计算 |
| `durationMin` | number | 是* | 240 | 硬 | 与 `endTime` 二选一；60–720 |
| `startTime` | `HH:mm` | 否 | 14:00 | 软 | 用于生成时间轴 |
| `endTime` | `HH:mm` | 否 | 空 | 硬 | 给定则换算时长上限 |
| `interests` | string[] | 否 | [] | 软 | 6 类兴趣 |
| `budgetMax` | number | 否 | null | 硬 | 0–10000；未指定则显示「未指定」 |
| `budgetBasis` | `total`/`per_person` | 否 | total | 硬 | 预算口径 |
| `party` | enum | 否 | solo | 软 | solo/friends/couple/family |
| `walkingTolerance` | enum | 否 | mid | 硬 | light/mid/deep → 最大步行 3/6/10 km |
| `transport` | enum | 否 | walk | 软 | walk/mix/bike（MVP 距离按步行估算） |
| `pace` | enum | 否 | mid | 软 | light/mid/deep（停留与地点密度） |
| `foodPreferences` | string[] | 否 | [] | 软 | 素食/不吃辣/本地小吃等 |
| `accessibility` | string[] | 否 | [] | 硬（unknown） | 无障碍需求；无数据时标 unknown，不声称满足 |
| `weather` | enum | 否 | any | 软 | rain/sunny/hot/cold；rain 偏好室内 |
| `avoid` | string[] | 否 | [] | 硬 | 类别或地点 id |
| `mustVisit` | string[] | 否 | [] | 硬 | 地点名或 id；无法匹配 → 冲突 |
| `additionalRequirements` | string | 否 | '' | 软 | ≤200 字，不直接执行 |

\* 缺 `durationMin` 且缺 `endTime` 时视为缺失，触发追问。

### 7.2 硬约束 / 软偏好

- **硬**：时长上限（含 5% 缓冲）、预算上限、必去点、避开项、步行上限、无障碍（可验证部分）。
- **软**：兴趣匹配、节奏、地点多样性、室内偏好、拍照倾向、评分。
- **冲突处理**：任何硬约束无法满足 → 不得静默放宽；返回 `conflict`，给出可选方案，由用户决定后重新生成。

### 7.3 评分（初始假设，可配置）

`overall = 0.35*interest + 0.20*timeFit + 0.15*efficiency + 0.15*budgetFit + 0.15*diversity`

- 权重存于 `server/config/scoring.json`，文档标注「初始假设，无用户研究依据，支持 A/B」；
- 评分只用于排序与解释，不替代硬约束校验；
- 页面展示分项与「为什么」文本，不只给总分。

### 7.4 路线对象（Route v1）

见 `docs/ARCHITECTURE.md` 的 Schema；关键字段：`id/city/name/source/conditions/places[]/segments[]/durationMin/actualMin/distanceKm/budget/scores/constraints[]/conflict/explanations[]/sources[]/dataQuality/degraded`。

### 7.5 数据规则

- 地点 id 唯一；路线中的 `placeId` 必须存在于目录；
- 同一路线不重复地点；
- 未核验营业时间一律 `null`，界面显示「信息待确认」；
- 坐标只有来自可追溯来源才填 `lat/lng`，否则为 `null` 并标注；
- 距离：有真实坐标用 Haversine × 1.25 系数估算；无坐标用示意坐标估算；两者都标「估算，非导航结果」；
- 预算：按地点示例消费区间求和；标「示例数据」；
- 时间轴：由 `startTime` 推算，标「估算」。

## 8. Agent / Workflow 需求

### 8.1 职责边界

- **Agent（LLM）**：理解自然语言、意图分类、抽取条件、生成解释文案、在远程模式下提出路线草案。
- **Workflow（确定性代码）**：候选检索、过滤、排序、时间/预算/距离计算、硬约束校验、Schema 校验、降级、日志。
- **禁止**：让 LLM 独自计算距离、时间、预算或可行性；所有数字必须由代码复算，LLM 输出仅作为候选。

### 8.2 工作流节点（13 步）

1 输入清洗 → 2 意图识别 → 3 需求结构化 → 4 缺失信息检查 → 5 候选获取 → 6 数据标准化 → 7 候选过滤 → 8 路线排序 → 9 时间/预算计算 → 10 硬约束校验 → 11 结果生成 → 12 Schema 校验 → 13 重试/降级。

每步的输入/输出、错误分支见 `docs/AGENT-WORKFLOW.md`。

### 8.3 结构化输出

- 定义 JSON Schema（`server/agent/schema.js`），服务端与前端共用；
- 远程输出校验失败：修复重试 ≤2 次（把校验错误回传给模型），仍失败返回 `INVALID_OUTPUT`；
- 前端对响应二次校验；非法数据不渲染。

### 8.4 Prompt 与工具

- 系统 Prompt 明确角色、约束、输出 Schema、拒绝提示注入；
- 工具调用（远程模式）：`getCandidatePlaces`、`validateRoute`、`computeMetrics`；模型只能通过工具拿事实；
- Prompt 版本化（`server/agent/prompts/*.md`），记录在文档。

### 8.5 RAG 取舍

- 候选价值：地点历史文化背景、路线主题解释；
- 先验证语料可得性（维基百科/官方文旅，带许可与来源）；若语料足够，实现**最小可运行检索**（TF-IDF/BM25，本地，无外部 embedding 服务）+ 引用来源 + 10 条查询评测；语料不足则**不做 RAG**，用结构化字段 + 模板解释，并在 `RAG-DESIGN.md` 说明理由。
- RAG 不替代实时搜索、营业状态、距离计算与导航。

**验证结果（2026-10-26，追加）**：本机网络无法访问 zh/en.wikipedia.org、api.wikimedia.org、www.wikidata.org、archive.org、openstreetmap.org 与 Nominatim；可访问的 360 百科文本为第三方版权内容，仅可用于内部核验，不能进入产品。可追溯的只有 OpenStreetMap 坐标（ODbL 1.0）。因此**本期不实现 RAG**，改用结构化地点属性 + 确定性规则 + 模板化理由 + 来源字段；未来设计与评测方案见 `docs/RAG-DESIGN.md`。这是对 8.5 条件分支的执行结果，不改变已确认的产品范围。

## 10. 接口定义

### 10.1 `POST /api/agent/run`

请求：

```json
{
  "requestId": "uuid（可选）",
  "traceId": "uuid（可选，缺省由服务端生成）",
  "task": "plan",
  "payload": { "conditions": { "...": "Conditions v1" } }
}
```

`refine` 的 payload：`{ "text": "少走一点路", "route": { "...": "Route v1" } }`。

响应（200）：

```json
{
  "code": 0,
  "requestId": "…", "traceId": "…", "task": "plan",
  "mode": "mock",
  "degraded": false,
  "data": { "...": "Route v1 或 RefineResult v1" },
  "meta": { "durationMs": 42, "provider": "mock-rules", "schemaVersion": "route.v1" }
}
```

错误（4xx/5xx）：

```json
{ "code": "INVALID_INPUT", "message": "可读说明", "details": [{"path":"payload.conditions.city","reason":"required"}],
  "requestId": "…", "traceId": "…" }
```

错误码：`INVALID_INPUT` 400、`NOT_FOUND` 404、`RATE_LIMITED` 429、`UPSTREAM_TIMEOUT` 504、`UPSTREAM_ERROR` 502、`INVALID_OUTPUT` 502、`INTERNAL` 500。

### 10.2 其他接口

- 静态资源：`GET /`、`/css/*`、`/js/*`、`/assets/*`

完整字段、错误分支、鉴权与透传规则见 `docs/API-INTEGRATION.md` 与 `docs/ARCHITECTURE.md`。

## 12. 埋点事件与指标口径

### 12.1 事件（客户端）

`plan_started`、`clarify_shown`、`clarify_answered`、`plan_succeeded`、`plan_failed`、`refine_started`、`refine_succeeded`、`refine_failed`、`conflict_shown`、`conflict_option_clicked`、`route_saved`、`route_exported`、`route_copied`、`agent_degraded`、`map_failed`、`retry_clicked`。

公共字段：`event`、`ts`、`routeId?`、`mode`、`appVersion`、`durationMs?`、`errorCode?`；**不含**自由文本与个人条件。

### 12.2 指标（摘要）

| 指标 | 分子/分母 | 数据来源 | 误判风险 |
| --- | --- | --- | --- |
| 规划任务成功率 | `plan_succeeded` / `plan_started` | 埋点 | 用户中途放弃算失败 |
| 约束满足率 | 满足的硬约束数 / 适用硬约束数 | 服务端评测 + 埋点 | 未验证约束按 unknown 不计入分子 |
| 必填识别准确率 | 正确识别的必填项 / 标注必填项 | 离线标注集 | 标注主观 |
| 路线结构有效率 | 通过 Schema 的路线 / 生成路线 | 评测 | Schema 通过 ≠ 业务正确 |
| 地点数据可验证率 | 有来源的地点 / 全部地点 | 数据审计 | 来源质量不一 |
| 调整成功率 | `refine_succeeded` / `refine_started` | 埋点 | 用户指令本身不可执行 |
| 首次有效路线耗时 | 从 `plan_started` 到首个合法 Route 的 P50/P90 | 埋点/评测 | Mock 与真实服务不可混比 |
| 错误恢复成功率 | 重试后成功 / 失败后重试 | 埋点 | 样本少 |
| 主动重新规划比例 | 同会话重复 plan / 会话数 | 埋点 | 正常改需求被算作负面 |
| 保存/复制比例 | `route_saved`+`route_exported` / `plan_succeeded` | 埋点 | 无真实流量 |

> 没有真实用户数据前，不报告转化率、留存或增长；只报告离线评测结果与可采集口径。完整定义见 `docs/PRODUCT-METRICS.md`。

## 15. 风险、限制与迭代计划

### 15.1 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |

| 作品集夸大风险 | 可信度受损 | 所有结论标注证据/未验证；最终报告附命令与输出 |

| 数据库/存储 | 无服务端数据库；浏览器 `localStorage` | MVP 无需账号；隐私边界清晰 |
| 测试框架 | `node:test` + `assert`；UI 用 `jsdom`（唯一 **devDependency**） | 内置、无额外运行时；DOM 测试可复现 |

| 远程 LLM | OpenAI 兼容 HTTP + Coze 适配器（均需服务端密钥） | 不绑定厂商；密钥不出服务端 |
